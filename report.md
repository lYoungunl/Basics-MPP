# Отчет по проекту DWH в Greenplum

## 1. Архитектура и проектные решения

В рамках проекта построено распределенное хранилище данных по схеме **STG → DDS → CDM**.

**Слой STG** содержит сырые данные, загруженные через INSERT с генерацией. Таблицы распределены по ключам (`DISTRIBUTED BY`), а таблица `orders` партиционирована по месяцам по полю `order_dt`. 
Особое внимание уделено генерации заказов: чтобы избежать перекоса данных и обеспечить сходимость с витриной, заказы генерируются строго внутри временных окон кампаний (дата = start_dt + случайное смещение), а клиенты выбираются только те, кто зарегистрировался до даты заказа (`signup_dt <= order_dt`). Ключ распределения для `stg.order_items` и `dds.fact_order_items` — `order_id`, чтобы избежать пересылки данных (Redistribute Motion) при соединении с заказами.

**Слой DDS** содержит измерения (`dim_customers`, `dim_channels`, `dim_campaigns`) и факты (`fact_orders`, `fact_order_items`). Добавлены служебные колонки `load_dt` и `load_src`. Факт `fact_orders` также партиционирован по дате.

**Слой CDM** представлен витриной `dm_sales_performance`, которая агрегирует данные по дням, кампаниям и каналам. В расчетах участвуют **только завершенные заказы** (`order_status = 'completed'`).

### Логика расчета производных метрик:
- `spend` — ежедневная доля бюджета кампании. Для избежания ошибок округления бюджет делится на точное количество дней кампании, а для последнего дня используется корректировка (бюджет минус сумма предыдущих дней). Это гарантирует, что сумма всех ежедневных `spend` в точности равна бюджету кампании.
- `revenue` — сумма завершенных заказов.
- `roi` — (revenue - spend) / spend.
- `new_customers` — количество клиентов, сделавших свой **первый заказ в целом** (без привязки к конкретной кампании) в этот день.

## 3. Оптимизация и проверки качества

- **Партиционирование:** Таблицы `orders` и `fact_orders` партиционированы по месяцам, что позволяет избежать полного сканирования при фильтрации по датам.
- **Распределение:** Выбраны ключи `DISTRIBUTED BY`, соответствующие полям соединения (JOIN). Для `order_items` выбран `order_id`, что ускоряет соединение с `orders` и исключает `Redistribute Motion` из плана.
- **ANALYZE:** После загрузки данных выполнена команда `ANALYZE` для обновления статистики.
- **Проверки качества:** В скрипт `04_reports.sql` добавлены проверки:
  - Отсутствие отрицательных метрик (0 строк).
  - Корректность новых клиентов (0 строк).
  - Точное соответствие затрат бюджетам (0 строк).
  - **Сходимость выручки CDM и DDS** (cdm_revenue = dds_revenue = 365986.65, diff = 0.00).
