# Отчет по проекту DWH в Greenplum

## 1. Архитектура и проектные решения

В рамках проекта построено распределенное хранилище данных по схеме **STG → DDS → CDM**.

**Слой STG** содержит сырые данные, загруженные через INSERT с генерацией. Таблицы распределены по ключам (`DISTRIBUTED BY`), а таблица `orders` партиционирована по месяцам по полю `order_dt` для ускорения запросов по датам.

**Слой DDS** содержит измерения (`dim_customers`, `dim_channels`, `dim_campaigns`) и факты (`fact_orders`, `fact_order_items`). Добавлены служебные колонки `load_dt` и `load_src`. Факт `fact_orders` также партиционирован по дате.

**Слой CDM** представлен витриной `dm_sales_performance`, которая агрегирует данные по дням, кампаниям и каналам. В расчетах участвуют **только завершенные заказы** (`order_status = 'completed'`).

### Логика расчета производных метрик:
- `spend` — ежедневная доля бюджета кампании (бюджет / 30).
- `revenue` — сумма завершенных заказов.
- `roi` — (revenue - spend) / spend.
- `new_customers` — количество клиентов, сделавших первый заказ в рамках кампании.

## 3. Оптимизация

- **Партиционирование:** Таблицы `orders` и `fact_orders` партиционированы по месяцам, что позволяет избежать полного сканирования при фильтрации по датам.
- **Распределение:** Выбраны ключи `DISTRIBUTED BY`, соответствующие полям соединения (JOIN).
- **ANALYZE:** После загрузки данных выполнена команда `ANALYZE` для обновления статистики.
- **EXPLAIN:** Проверка плана запроса показала использование `GPORCA` и эффективное распределение агрегаций по сегментам (Gather Motion / Redistribute Motion), что минимизирует пересылку данных.
