# Отчет по проекту DWH в Greenplum

## 1. Архитектура и проектные решения

В рамках проекта построено распределенное хранилище данных по схеме **STG → DDS → CDM**.

**Слой STG** содержит сырые данные, загруженные через INSERT с генерацией. Таблицы распределены по ключам (`DISTRIBUTED BY`), а таблица `orders` партиционирована по месяцам по полю `order_dt` для ускорения запросов по датам. Для таблицы `stg.order_items` в качестве ключа распределения выбран `order_id`, чтобы избежать пересылки данных (Redistribute Motion) при соединении с таблицей заказов.

**Слой DDS** содержит измерения (`dim_customers`, `dim_channels`, `dim_campaigns`) и факты (`fact_orders`, `fact_order_items`). Добавлены служебные колонки `load_dt` и `load_src`. Факт `fact_orders` также партиционирован по дате. Ключ распределения для `fact_order_items` изменен на `order_id` для оптимизации JOIN.

**Слой CDM** представлен витриной `dm_sales_performance`, которая агрегирует данные по дням, кампаниям и каналам. В расчетах участвуют **только завершенные заказы** (`order_status = 'completed'`).

### Логика расчета производных метрик:
- `spend` — ежедневная доля бюджета кампании. Для избежания ошибок округления бюджет делится на точное количество дней кампании, а для последнего дня используется корректировка (бюджет минус сумма предыдущих дней). Это гарантирует, что сумма всех ежедневных `spend` в точности равна бюджету кампании.
- `revenue` — сумма завершенных заказов.
- `roi` — (revenue - spend) / spend.
- `new_customers` — количество клиентов, сделавших первый заказ в рамках кампании.

## 3. Оптимизация и проверки

- **Партиционирование:** Таблицы `orders` и `fact_orders` партиционированы по месяцам, что позволяет избежать полного сканирования при фильтрации по датам.
- **Распределение:** Выбраны ключи `DISTRIBUTED BY`, соответствующие полям соединения (JOIN). Для `order_items` выбран `order_id`, что ускоряет соединение с `orders`.
- **ANALYZE:** После загрузки данных выполнена команда `ANALYZE` для обновления статистики.
- **EXPLAIN:** Проверка плана запроса показала использование `GPORCA` и эффективное распределение агрегаций по сегментам (Gather Motion / Redistribute Motion), что минимизирует пересылку данных.
- **Проверки качества:** В скрипт `04_reports.sql` добавлены проверки, которые подтверждают отсутствие отрицательных метрик, корректность количества новых клиентов и точное соответствие затрат бюджетам (проверка `diff` выдает 0 строк).
